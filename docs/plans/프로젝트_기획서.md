## 1. 프로젝트 개요

고객의 ITSM 요구사항 문서를 입력받아 기능 명세서, ERD, DDL 초안을 생성하고, 요구사항과 설계 결과의 연결 관계를 추적하여 누락과 모순을 검토하는 웹 기반 에이전트를 개발한다.

대상 업무는 **서비스 요청 및 장애 관리**로 한정한다. 실제 ITSM 업무를 처리하는 시스템을 구축하는 것이 아니라, 해당 시스템을 구축하기 위한 **기능 및 데이터 설계 초안을 자동으로 생성하고 검토하는 도구**를 구현한다.

본 기획서의 개발 일정, 역할 배분, 기술 구성 및 정량 목표는 계획안이다. 실제 팀 인원, 교육 일정, 사용 가능한 모델과 예산에 맞춰 착수 시 확정한다. 업무 사례는 가상의 기업을 기준으로 하며, 특정 기업의 실제 내부 정책을 전제하지 않는다.

## 2. 추진 배경과 문제 정의

시스템 구축 초기에는 고객 문서에서 요구사항을 추출하고, 이를 구현할 기능과 데이터 구조로 구체화해야 한다. 이 과정에서 같은 내용을 여러 산출물에 옮겨 적거나, 문서에 명확하지 않은 정책을 확인하고, 설계 변경에 따라 관련 산출물을 함께 수정해야 한다.

서비스 요청과 장애 관리에는 승인, 담당자 배정, 상태 변경, 처리 이력 등 서로 연결된 규칙이 존재한다. 예를 들어 ‘승인 이력을 보관한다’는 요구사항이 기능 명세에는 반영되어도 데이터 모델에 이력 저장 구조가 없으면 설계가 불완전해진다.

본 프로젝트는 다음 문제를 해결하고자 한다.

- 자연어 요구사항을 기능과 데이터 설계로 변환하는 초기 작업의 부담
- 요구사항, 기능 명세, 데이터 모델 사이의 연결 누락
- 정보가 부족한 업무 규칙을 설계자가 임의로 해석할 가능성
- 설계 결과의 누락·모순을 문서별로 대조해야 하는 검토 부담

## 3. 프로젝트 목표

### 3.1 기능 목표

1. 요구사항 문서에서 개별 요구사항을 추출하고 기능·비기능 요구사항으로 분류한다.
2. 요구사항에 근거한 기능 목록과 기능 명세서 초안을 생성한다.
3. 기능을 수행하는 데 필요한 엔티티·속성·관계를 도출하고 ERD와 DDL을 생성한다.
4. 요구사항과 기능·테이블의 연결을 추적표로 제공한다.
5. 입력 문서와 설계 결과의 누락·모순·불명확한 사항을 검토한다.

### 3.2 품질 목표

생성 결과에는 원문 근거와 요구사항 ID를 연결한다. 문서에 명시된 사실, 설계를 위한 제안, 사용자 확인이 필요한 사항을 구분한다. 생성된 설계는 검토 가능한 초안으로 제공하며, 모델의 판단만으로 업무 정책이 확정되었다고 표시하지 않는다.

구조와 SQL의 유효성은 프로그램으로 검사하고, 업무 의미의 적절성은 기준 답안과 사람의 검토로 평가한다. 처리 시간과 모델 사용량은 실제 실행에서 측정하여 보고한다.

## 4. 대상 업무와 범위

### 4.1 서비스 요청 관리

대표 사례는 계정 발급과 시스템 접근 권한 신청이다. 요청 등록, 승인·반려, 담당자 처리, 완료, 재신청 및 이력 보관을 요구사항으로 다룬다. 다단계 승인과 요청 유형별 규칙은 예외 시나리오로 포함한다.

### 4.2 장애 관리

대표 사례는 업무 시스템 접속 장애와 서비스 기능 오류 신고다. 장애 접수, 영향도·긴급도에 따른 우선순위, 담당자 배정, 처리 상태 변경, 해결 확인, 재개 및 처리 이력을 다룬다. 우선순위 산정 규칙 등 세부 정책은 입력 문서에 정의된 값을 따르거나 확인 필요 사항으로 남긴다.

### 4.3 MVP 포함 범위

| 구분 | 구현 범위 |
| --- | --- |
| 문서 입력 | 텍스트 기반 PDF·DOCX·TXT 업로드와 텍스트 추출 |
| 요구사항 분석 | ID 부여, 기능·비기능 분류, 원문 위치 연결, 확인 필요 사항 표시 |
| 기능 명세 | 기능 ID, 설명, 입력·출력, 선행 조건, 처리 규칙, 예외, 우선순위 |
| 데이터 설계 | 엔티티·속성·관계, PK·FK, 필수 여부, 기본 제약조건, 테이블 정의 |
| ERD·DDL | ERD 시각화와 단일 DB 방언의 테이블 생성 SQL 제공 |
| 추적표 | 요구사항 ID ↔ 기능 ID ↔ 테이블·컬럼 연결 및 연결 근거 |
| 설계 검토 | 미반영 요구사항, 존재하지 않는 참조, 모순 후보, 정보 부족 항목 표시 |
| 사용자 확인 | 확인 필요 항목에 대한 답변 입력과 수정 문서를 통한 재생성 |
| 결과 관리 | 실행 상태·실패 사유 조회, 실행별 결과 저장, 산출물 다운로드 |

### 4.4 MVP 제외 범위

- 실제 계정 생성, 권한 부여, 장애 티켓 처리 등 ITSM 운영 기능
- 실제 기업 시스템, 그룹웨어, 자산 관리 시스템과의 연동
- 변경 관리, 문제 관리, 전체 구성 관리 등 ITSM 전 영역의 설계
- 스캔 문서 OCR, 복잡한 이미지·도형 중심 문서 해석
- 고객 시스템의 애플리케이션 소스코드 및 배포 환경 자동 생성
- 운영 DB에 대한 생성 SQL 자동 실행
- 다중 DB 지원, 공동 편집, 정교한 버전 병합과 부분 재설계

## 5. 사용자와 이용 흐름

업무 분석가는 요구사항을 정리하고 불명확한 사항을 확인한다. 설계자와 개발자는 생성된 기능·데이터 모델 및 연결 근거를 검토하고 개발을 위한 초안으로 활용한다.

1. 사용자가 프로젝트를 만들고 요구사항 문서를 업로드한다.
2. 시스템이 텍스트를 추출하고 요구사항 목록과 확인 필요 항목을 보여준다.
3. 사용자가 필요한 설명을 보완한다. 미해결 항목이 있으면 해당 설계가 잠정적임을 표시한다.
4. 에이전트가 기능 명세와 데이터 모델을 생성한다.
5. 시스템이 데이터 모델에서 ERD와 DDL을 만들고 추적표를 구성한다.
6. 검토 단계에서 구조 오류와 업무상 누락·모순 후보를 표시한다.
7. 사용자가 검토 결과를 확인하고 필요한 경우 입력을 보완하여 재생성한다.
8. 기능 명세, 데이터 설계, SQL, 추적표 및 검토 보고서를 다운로드한다.

주요 화면은 프로젝트·문서 등록, 요구사항 확인, 기능 명세, ERD·테이블 정의, 추적표·검토 결과의 다섯 영역으로 구성한다. 생성 진행 상태와 오류는 해당 화면에서 확인할 수 있도록 한다.

## 6. 주요 기능 명세

아래 ID는 우리가 개발할 에이전트의 기능을 식별한다. 고객 문서를 분석하여 생성하는 요구사항·기능 ID와는 별도로 관리한다.

| ID | 기능 | 주요 동작 | 완료 조건 |
| --- | --- | --- | --- |
| AG-01 | 문서 입력·추출 | 지원 형식 확인, 텍스트와 원문 위치 추출 | 추출 결과 확인 및 빈 문서·미지원 형식 오류 안내 |
| AG-02 | 요구사항 분석 | 요구사항 분리, 분류, 근거 연결 | 각 요구사항에 고유 ID와 근거 또는 제안 표시 |
| AG-03 | 불명확 항목 확인 | 정보 부족·상충 후보와 확인 질문 제공 | 답변 또는 미해결 상태가 다음 설계 단계에 전달 |
| AG-04 | 기능 명세 생성 | 기능별 입력·출력·규칙·예외 정의 | 요구사항 연결과 필수 필드 검증 통과 |
| AG-05 | 데이터 모델 생성 | 엔티티·속성·관계·키·제약 정의 | 테이블·컬럼 ID와 관계 참조 유효성 확인 |
| AG-06 | ERD·DDL 생성 | 공통 모델에서 시각화와 SQL 생성 | ERD·DDL 구조 일치 및 테스트 DB 생성 검증 |
| AG-07 | 추적표 생성 | 요구사항·기능·테이블의 연결 표시 | 누락·잘못된 참조·연결 불필요 항목 구분 |
| AG-08 | 누락·모순 검토 | 규칙 검사와 의미 검토 수행 | 근거, 관련 ID, 문제 설명, 수정 제안 제공 |
| AG-09 | 결과 저장·내보내기 | 실행별 결과와 검토 상태 저장 | 재조회 및 문서·CSV·SQL 다운로드 가능 |

비기능 요구사항은 별도 검증 항목과 연결할 수 있다. 모든 요구사항에 테이블 연결을 강제하지 않으며, 연결이 필요하지 않은 경우 이유를 기록한다.

## 7. 에이전트 처리 구조

### 7.1 단계별 책임

| 단계 | 입력 | 처리 | 출력 |
| --- | --- | --- | --- |
| 분석 | 문서 텍스트·원문 위치 | 요구사항 추출·분류, 불명확 항목 식별 | 요구사항 목록·질문 |
| 기능 설계 | 요구사항·사용자 답변 | 기능 및 업무 규칙 구체화 | 구조화된 기능 명세 |
| 데이터 설계 | 요구사항·기능 명세 | 엔티티·속성·관계 도출 | 구조화된 데이터 모델 |
| 산출물 변환 | 공통 데이터 모델·연결 정보 | ERD·DDL·추적표 변환 | 설계 파일·연결 목록 |
| 검토 | 원문·요구사항·전체 설계 | 구조 검사, 누락·모순 후보 검토 | 검토 결과·수정 제안 |

각 단계는 명시적인 입력·출력 스키마를 가진다. 초기 구현은 순차 실행으로 구성하고, 독립적인 복수 에이전트 운영 여부는 구현 난이도와 평가 결과에 따라 결정한다.

### 7.2 검증과 보완 원칙

- JSON 스키마, ID 중복, 참조 무결성, 필수 필드, 키·타입 호환성은 코드로 검증한다.
- ERD와 DDL은 동일한 데이터 모델에서 생성하여 표현 간 불일치를 줄인다.
- 누락과 의미상 모순은 LLM이 원문 근거와 함께 후보로 제시하고 사람이 확인한다.
- 형식 오류 등 자동 수정 가능한 항목은 오류 정보를 전달해 제한적으로 재시도한다. 초기 상한은 단계별 1회로 제안한다.
- 승인 권한·예외 정책 등 업무 판단은 자동으로 확정하지 않는다. 미해결이면 검토 필요 상태로 남긴다.
- 재생성 결과는 기존 결과를 덮어쓰지 않고 실행 단위로 구분한다. MVP에서는 전체 재생성을 기본으로 한다.

### 7.3 기술 구성안

웹 UI, 백엔드 API, 단계 실행 모듈, LLM API, 결과 저장 DB와 파일 저장소로 구성한다. 현재 작업 폴더를 프로젝트 루트로 삼아 새로 개발하며, 기술 스택은 팀의 숙련도와 요구사항을 확인한 후 확정한다.

초기 후보는 React 기반 UI, Python·FastAPI 백엔드, PostgreSQL 저장소와 SQL 검증 환경이다. ERD는 구조화된 모델을 시각화할 수 있는 도구를 선정한다. 모델명은 구조화 출력 품질, 한국어 요구사항 해석, 비용 및 응답 시간을 소규모 샘플로 비교한 후 결정한다. MVP에서 벡터 DB나 별도의 에이전트 프레임워크를 필수 구성으로 두지 않는다.

우리 서비스의 저장 대상은 프로젝트, 입력 문서, 생성 실행, 요구사항, 기능 명세, 데이터 모델, 추적 연결, 검토 결과이다. 고객용 ERD의 요청·승인·장애 테이블과 우리 서비스의 저장 구조는 구분한다.

문서 본문은 분석할 데이터로 취급하며, 본문에 포함된 명령으로 실행 정책이나 도구 권한을 변경하지 않는다. 모델 키는 서버에서 관리하고, 실행 로그에는 키와 문서 전문이 불필요하게 노출되지 않도록 한다. SQL 실행 검증은 외부 서비스 접근 권한이 없는 폐기 가능한 테스트 DB에서 허용된 DDL만 대상으로 수행한다.

## 8. 대표 시연 시나리오

### 8.1 서비스 요청 설계 생성

**입력 예시:** 직원이 운영 시스템 접근 권한을 신청하면 팀장과 보안 담당자가 순차 승인한다. 반려된 신청은 수정 후 다시 제출할 수 있고, 모든 승인 이력을 보관한다.

**기대 결과:** 신청, 순차 승인, 반려, 재신청, 이력 보관 기능이 도출된다. 데이터 모델은 신청과 승인 단계·기록을 표현하고, 관련 요구사항과 기능·테이블이 연결된다. 재신청 시 승인 단계를 어디부터 다시 시작하는지가 불명확하면 확인 필요 사항으로 표시한다.

### 8.2 장애 처리 설계 생성

**입력 예시:** 사용자가 서비스 장애를 신고하면 담당자가 배정된다. 담당자는 조치 내용을 기록하고 해결 상태로 변경하며, 신고자가 해결을 확인하면 종료한다. 종료 이후에도 장애를 재개할 수 있고 이전 처리 이력을 유지한다.

**기대 결과:** 장애 접수, 배정, 조치 기록, 해결 확인, 종료, 재개 기능과 이력 구조를 생성한다. 재개 권한이나 재개 후 상태가 명시되지 않았다면 확인 질문을 제시한다.

### 8.3 정보 부족과 상충 조건 검토

**입력 예시:** 문서의 한 항목에는 ‘모든 권한 신청은 사전 승인이 필요하다’고 하고, 다른 항목에는 ‘긴급 신청은 승인 없이 즉시 처리할 수 있다’고 기재한다.

**기대 결과:** 두 원문을 함께 제시하고 긴급 신청이 예외인지, 적용 조건과 사후 승인 정책이 필요한지 확인한다. 예외 여부를 확정하지 않은 상태에서 오류라고 단정하거나 정상 정책으로 자동 확정하지 않는다.

### 8.4 설계 누락 발견

평가용 설계에서 승인 이력 저장 구조를 의도적으로 제거한다. 검토 단계가 이력 보관 요구사항과 관련 기능을 근거로 누락을 탐지하는지 확인한다. 추적 링크만 없어진 경우와 실제 설계 요소가 없어진 경우를 구분하여 보고한다.

## 9. 평가 데이터와 검증 계획

### 9.1 가상 요구사항 문서 구성

5~10건 범위에서 **8건**을 초기 구성안으로 제안한다. 각 문서는 하나의 고객 요구사항 정의서로 작성하고, 요구사항 목록·필수 기능·데이터 제약·확인 필요 항목을 기준 답안으로 준비한다.

| 문서 | 업무 | 조건 | 주요 평가 내용 |
| --- | --- | --- | --- |
| D01 | 서비스 요청 | 기본 | 단일 승인과 요청 처리 |
| D02 | 장애 관리 | 기본 | 접수·배정·해결·종료 |
| D03 | 서비스 요청 | 예외 | 순차 승인·반려·재신청 |
| D04 | 장애 관리 | 예외 | 담당자 변경·재개·이력 보존 |
| D05 | 서비스 요청 | 정보 부족 | 긴급 처리와 승인 생략 조건 미정 |
| D06 | 장애 관리 | 정보 부족 | 우선순위·종료 권한 규칙 미정 |
| D07 | 서비스 요청 | 상충 | 사전 승인 원칙과 즉시 처리 규칙 충돌 후보 |
| D08 | 장애 관리 | 상충 | 종료 가능 주체·조건의 상이한 정의 |

이 중 기본·예외·정보 부족·상충 사례를 한 건씩 포함한 4건은 개발에 사용하고, 나머지 4건은 최종 평가 전까지 프롬프트 조정에 사용하지 않는다. 최종 평가 후 수정이 이루어지면 변경 내용과 재평가 여부를 기록한다. 소규모 가상 문서 평가 결과를 실제 기업 문서 전체에 대한 성능으로 일반화하지 않는다.

### 9.2 평가 지표와 초기 목표

아래 수치는 달성 실적이 아닌 제안 목표다. 명칭이 다른 동등한 설계도 인정할 수 있도록 기능과 데이터 모델의 의미를 기준으로 채점한다.

| 평가 항목 | 측정 방법 | 초기 목표 |
| --- | --- | --- |
| 요구사항 추출 재현율 | 올바르게 추출한 기준 요구사항 수 ÷ 기준 요구사항 수 | 90% 이상 |
| 요구사항 추출 정밀도 | 올바른 추출 요구사항 수 ÷ 전체 추출 요구사항 수 | 90% 이상 |
| 필수 기능 반영률 | 설계에 반영된 기준 필수 기능 수 ÷ 전체 기준 필수 기능 수 | 90% 이상 |
| 핵심 데이터 규칙 충족률 | 모델로 표현 가능한 기준 규칙 수 ÷ 전체 기준 규칙 수 | 90% 이상 |
| 추적 연결 정확도 | 검토자가 타당하다고 판정한 연결 수 ÷ 생성 연결 수 | 90% 이상 |
| 추적 연결 충족률 | 필요한 설계 연결을 갖춘 요구사항 수 ÷ 연결 대상 요구사항 수 | 90% 이상 |
| 문제 탐지 재현율 | 탐지한 기준 문제 수 ÷ 의도적으로 포함한 기준 문제 수 | 80% 이상 |
| 문제 탐지 정밀도 | 타당한 문제 지적 수 ÷ 전체 문제 지적 수 | 80% 이상 |
| DDL 실행 성공률 | 테스트 DB에서 생성에 성공한 평가 실행 수 ÷ 전체 평가 실행 수 | 100% |
| ERD·DDL 일치 | 테이블·컬럼·키·관계 구조 비교 | 불일치 0건 |

비율은 문서별 결과와 전체 분자·분모를 함께 제시한다. 평가 대상이 없는 항목은 N/A로 처리한다. 미응답·생성 실패도 기록하고 성공한 결과만 골라 보고하지 않는다. 최종 평가 문서는 동일 설정으로 각 3회 실행하여 결과 변동을 확인하고, 실행 시간·모델 사용량·실패 및 재시도 횟수를 함께 기록한다.

두 명의 팀원이 기준 답안과 결과를 교차 검토하고, 의견이 다른 항목은 근거를 기록해 합의한다. 모델의 자기평가만으로 통과 여부를 결정하지 않는다. 평가 시작 전에 모델·프롬프트·스키마 버전과 지표를 고정한다.

## 13. 완료 기준과 기대 효과

프로젝트는 다음 조건을 만족했을 때 MVP 구현을 완료한 것으로 판단한다.

- 지원 문서를 입력하여 요구사항 분석부터 결과 다운로드까지 실행할 수 있다.
- 기능 명세, ERD, DDL, 추적표, 검토 보고서가 생성된다.
- 원문 근거와 확인 필요 사항을 조회할 수 있다.
- 서비스 요청과 장애 관리 각각의 기본 시나리오가 동작한다.
- 정보 부족·상충 조건 및 의도적으로 주입한 설계 누락을 검토하는 시연이 가능하다.
- 생성 DDL의 테스트 DB 실행 결과와 산출물 간 일치 여부를 기록한다.
- 가상 문서 5~10건, 기준 답안, 최종 평가 결과와 실패 사례를 제출한다.
- 제안 목표의 달성 여부를 실측치로 보고하고, 미달 항목은 원인과 개선 계획을 남긴다.

본 프로젝트를 통해 자연어 요구사항을 검토 가능한 설계 초안으로 변환하는 흐름을 구현한다. 교육 관점에서는 업무 분석, 데이터 모델링, LLM 출력 제어, 에이전트 단계 설계, 프로그램 검증과 사람의 평가를 연결하는 경험을 확보한다. 초기 설계 시간 절감과 품질 향상은 기대 효과로 두고, 실제 개선 정도는 평가 결과로 확인한다.
