# 첨부 핵심 로직과 제품 흐름 통합

- 버전·최종 수정일: 1.0 · 2026-10-16
- 상태: 진행 중. 현 `/design` 4단계 그래프의 파일 책임 분리는 검증을 마쳤다. 첨부 핵심 로직 이식·통합 검증은 아직 완료하지 않았다.
- 목적: 사용자 제공 `client_requirement-main.zip`에서 문서 분석과 단계별 설계의 유용한 로직을 골라 현재 ITSM 설계 에이전트의 구조·계약에 맞게 통합한다.
- 기준: [백엔드 통합 구조와 명명 규칙](../백엔드_통합_구조.md), [TRD](../TRD.md), [요구사항 정의서](../요구사항_정의서.md), [기능 명세서](../기능_명세서.md)
- 관련 ID: FR-001~020, NFR-001~014, BR-001~010, AG-00~09. 각 작업의 적용 범위는 아래 표에서 좁힌다.

## 범위와 진행 원칙

현재 `/api/v1/design`의 동기 텍스트 API, Anthropic 호출, 공통 모델 검증·ERD/DDL 렌더러와 테스트를 출발점으로 삼는다. 첨부 소스의 파일·패키지·설정·스키마를 통째로 옮기지 않고 [구조 문서의 배치 판단](../백엔드_통합_구조.md)에 따라 필요한 알고리즘과 테스트 사례를 이식한다. 운영 DB는 프로젝트·문서·실행을 저장하고, 고객용으로 생성한 DDL은 격리 검증 DB에서만 실행한다.

첫 리팩터링에서 현재의 `generate → validate → render → review`를 `design_pipeline/`의 그래프·상태·모델 호출·역할·검증/변환 노드로 분리했다. API 입출력과 4단계 분기는 유지했다. 이는 첨부 소스의 전문 역할 이식이나 문서/실행 저장 기능을 완료한 단계가 아니다. 분리된 각 파일은 [구조 문서의 현재 트리](../백엔드_통합_구조.md)를 따른다.

이번 통합의 목표는 PDF·DOCX·UTF-8 TXT 입력, 근거 확인, 질문과 답변, 기능·데이터 설계, 공통 모델의 ERD·DDL, 추적·검토, 실행 상태와 산출물 제공, 웹 UI 연결이다. HWPX·Markdown·CP949 입력 지원, CLI·manual LLM 공급자, SQLite로 PostgreSQL 성공을 대신하는 경로, 범용 변경 요청의 부분 재설계는 범위에서 제외한다. 후속 범위가 필요해지면 먼저 PRD·요구사항·기능 수용 기준을 변경한다.

작업은 아래 순서와 선행 조건대로 진행한다. 각 묶음은 관련 코드·필요한 기준 문서·테스트를 같은 변경에서 다루고, 현재 API를 바꾸는 시점은 계약 검사 통과 뒤로 둔다. `추가 예정` 파일 경로는 생성 계획일 뿐 구현 실적이 아니다.

## 역할별 작업 배치

기획·도메인·평가, AI·에이전트, 백엔드·데이터, 프론트엔드·통합의 네 책임 역할로 작업을 나눈다. 실명 담당과 일정은 아직 배정되지 않았으므로 작업 착수 시 팀이 표에 기록한다. 한 사람이 여러 역할을 겸임할 수 있지만 평가 기준 작성과 결과 판정은 교차 검토한다.

## A. 계약·전환 경계

이 절은 [기능 명세서의 상태·단계 정책](../기능_명세서.md)과 [TRD 3~6장](../TRD.md)을 코드 계약으로 옮긴 경계다. A의 스키마와 순수 검사·전이 함수는 작성되었으나 **새 그래프의 연결·통합 검증 완료를 뜻하지 않는다.** 기존 `POST /api/v1/design`은 동기 텍스트 입력의 회귀 기준으로 유지하고, 프로젝트·문서·실행 API 전환은 E에서 수행한다.

| 항목 | 현재 `/design` 계약 | 목표 단계 계약·전환 경계 |
| --- | --- | --- |
| 입력·실행 | `text` 1건, 1~12,000자; 한 HTTP 요청에서 4단계 실행, 실행 ID·재개 없음 | 불변 문서 리비전의 추출 블록을 분석 입력으로 사용한다. 실행 상태·답변 스냅샷·재개는 E의 저장/API 계약에 연결한다. |
| 원문 근거 | 요구사항·검토 결과에 인용 문자열만 보관하고 원문 부분 문자열과 대조 | 문서 리비전·블록 ID·정규화 문자열의 문자 시작/끝 위치·인용문을 참조하고 서버에서 해당 구간을 대조한다. 원문 위치는 블록에 보존한다. |

| `intake`·`document_analyst` | 등록된 문서 리비전·추출 블록 → 분석 가능한 블록·품질 상태 | 빈/실패 추출은 분석 완료가 아니다. 준비된 블록만 요구사항 분석으로 보낸다. |
| `requirements_analyst` → `inspect_result` | 한 리비전의 `AnalysisInput`(추출 블록) → `AnalysisOutput`(요구사항·확인 질문) | 입력 블록 ID 중복·리비전 혼합을 먼저 막고, 출력과 **해당 `AnalysisInput`**을 대조해 실행 내 ID 고유성·정확한 블록 구간 인용·출처·빈 요구 목록을 검사한다. 질문이 0개여도 분석 후 `awaiting_input`으로 간다. |
| `human_input` | 요구사항·질문·저장된 답변 버전 → 진행 결정·동결된 답변/미해결 스냅샷 | 답변 또는 미해결로 진행할 수 있다. 진행 결정 후 `queued`로 돌아가고, 미해결 여부는 동결 답변에서 전이 상태에 자동 반영한다. 재진입 때는 동결본만 기능·데이터 단계에 전달한다. |
| `function_designer` → `inspect_result` | 요구사항·동결 답변·미해결 질문 → 기능 목록 | `C-FUN-*` ID, 필수 필드, 존재하는 `requirement_ids[]` 참조를 검사한다. `user_answer` 출처는 동결본의 질문 ID·답변 버전과 일치해야 데이터 설계로 간다. |
| `data_modeler` → `inspect_result` | 요구사항·기능·동결 답변·미해결 질문 → 공통 `DataModelV1`·설계 근거 | 테이블·컬럼 ID와 키·FK·기능 참조를 검사한다. 답변 출처는 동결본과 대조하고, 키·자료형·관계의 의미 검사는 D의 공통 모델 규칙이 맡는다. 유효한 모델만 변환에 사용한다. |
| `structure_validation`·`artifact_render` | 요구사항·기능·공통 모델 → 구조·추적 검증 결과, 동일 모델의 ERD·DDL·추적표 | 구조 오류는 ERD·SQL 정식 제공을 차단한다. 검증된 같은 모델 버전과 해시를 각 산출물에 연결한다. |
| `reviewer`·`db_validation` | 원문·답변·설계·규칙 검사·DDL → 의미 검토 후보와 DB `passed/failed/not_run` | 답변 기반 검토 문제는 질문 ID·답변 버전으로 출처를 표시한다. 의미 검토 실패는 기술 실패다. DB 실패만으로 업무 설계를 자동 수정하지 않고, 미실행은 경고와 미검증 초안으로 남긴다. |
| `check_completion`·`deliver` | 누적 검증 결과·전이 상태의 미해결 여부·명시적인 검토 경고 결과 → 완료 상태·허용 파일 목록 | 기술 실패 → 구조·DDL 오류 → 미해결/검토 경고·DB 미실행 → 정상 완료 순으로 판정한다. 불가능한 검증 상태 조합과 이전 검사 결과 교체를 거부한다. 파일 해시·검증 상태가 맞는 산출물만 제공한다. |

| 현재 상태·사건 | 허용 다음 상태·분기 | 실패·재시도 계약 |
| --- | --- | --- |
| `queued`에서 작업자 선점 | `running(analysis)` 또는 동결 답변이 있는 재진입의 `running(design/review)` | 입력·문서 준비 오류나 활성 실행 충돌은 실행 성공으로 바꾸지 않는다. 작업자 선점·영속 트랜잭션은 E에서 구현한다. |
| `running(analysis)`의 요구사항·질문 검사 통과 | 질문 유무와 무관하게 `awaiting_input` | 출력 형식·근거 오류는 한도 내 복구 후에도 남으면 `failed`; 빈 요구 목록도 완료로 표시하지 않는다. |
| `awaiting_input`의 진행 결정 또는 문서 교체 | 답변 버전 동결 후 `queued`; 문서 교체 시 `superseded` | 미해결 선택을 허용하고 동결 답변에서 미해결 여부를 계산한다. 버전 충돌은 진행·동결을 거부하고 기존 대기 상태를 보존한다. |
| `running(design/review)`의 단계 통과·검증 | 다음 전문 역할·검사로 진행, 이후 `check_completion → deliver` | 단계 출력 실패를 정상 빈 결과로 대체하지 않는다. 기술 실패는 단계·코드·안내·재시도 가능 여부·시도 횟수를 가진 실패 정보와 함께 `failed`로 전이한다. 선행 산출물이 바뀌면 하위 산출물을 무효화한다. |
| 형식 복구 가능 오류·일시적 공급자 오류 | 동일 단계 한 번만 다시 시도 | 최초 시도 외 자동 재시도는 **단계당 최대 1회**, 두 오류 유형이 같은 한도를 공유한다. 잘못된 키·권한·입력 상한 초과는 자동 재시도하지 않는다. |
| 구조·DDL 검사 오류 또는 DB 환경 장애 | 각각 `completed_with_errors` 또는 `completed_with_warnings`(DB `not_run`) | 단계별 검증 결과를 누적하고 구조 실패 뒤 의미·DB 통과처럼 불가능한 조합과 이전 결과 교체를 거부한다. 제공 단계는 검토 경고 유무를 명시적으로 받아야 한다. 구조 오류는 ERD·SQL 차단, DDL 실행 실패는 SQL 배포용 다운로드 차단, DB 미실행은 미검증 초안만 허용한다. 기술 실행 실패는 별도 `failed`로 마감한다. |

## 이식 전 필수 실패 사례

첨부 소스에서 재현한 아래 동작은 통합 결과의 수용 조건으로 삼지 않는다. 담당 작업에 회귀 테스트를 추가해 차단한다.

| 담당 | 재현 조건 | 기대 결과 |
| --- | --- | --- |
| B·C | 한 본문 추출 배치가 실패하고 다른 배치가 성공 | 실패 단위와 원인이 남으며 전체 실행을 성공으로 표시하지 않는다. |
| B | 같은 절에 요구사항 표와 표 밖 의무 문장이 함께 있음 | 두 부분이 모두 추출 대상 또는 명시적 미추출 경고로 남는다. |
| B | 원문 `1.5초`, 생성 인용 `15초` | 근거 불일치로 검출한다. |
| C·D | 변경 기능에 새 입력 컬럼이 필요한데 기존 엔티티에만 연결됨 | 모델 속성 재검토 없이 최신·완료 판정을 하지 않는다. 부분 재설계를 지원하기 전까지는 새 실행에서 전체 재생성한다. |
| C | 비기능 요구사항의 보관 기간에 사용자가 답함 | 답변이 기능·데이터 설계 입력 및 결과 검토에 나타난다. |

## 현재 구현의 회귀 기준

기존 4단계 그래프를 대표 시나리오 3종으로 실제 호출했을 때 01 헬프데스크는 완료, 02 장애 대응은 `review`의 원문 인용 불일치(502 `invalid_review_reference`), 03 서비스 카탈로그는 추가 테이블의 PK·추적 누락(422 `structure_invalid`)으로 끝났다. 당시 모델은 `claude-haiku-4-5-20251001`, 출력 한도는 8192토큰이었다. 이 실측은 현재 버전의 일반 성공률이 아니라 단계 분리·오류 복구의 회귀 사례다. A·C에서 현 4단계의 입출력을 새 전문 역할로 나눌 경계를 정하고, 제한된 재시도 규칙은 한 그래프 경로에만 구현한다. 검증 규칙을 완화하거나 실패를 샘플 출력으로 대체하지 않는다.

현재 백엔드 동작과 첨부 저장 응답 재생은 각각의 기존 범위에서 얻은 증거다. 신규 통합의 동작·품질 통과로 이월하지 않는다. 작업별 기록에는 실행 명령, 통과/실패, 실제 LLM·격리 DB 미검증 범위, 변경한 파일과 관련 문서 버전을 남긴다.
