# 실제 모델 출력의 검증 실패 개선

- 버전·최종 수정일: 0.1 · 2026-10-07
- 상태: 예정 (검토 중인 제안, 구현 미착수)
- 사용자 목적: 대표 시나리오 같은 정상 입력이 실제 모델 실행에서도 안정적으로 200을 받도록 에이전트를 개선
- 기준: [기능 명세서 자동 재시도](../기능_명세서.md), [TRD 재시도 정책](../TRD.md), [002 시나리오 디버깅](002-시나리오-디버깅.md)

## 관찰한 현상

대표 시나리오를 고객이 보낸 요구사항 정의서 형태로 바꾼 뒤 실제 모델로 실행했다. 실행 명령은 `./debug-design all --mode live`, 모델은 claude-haiku-4-5-20251001, 출력 한도는 8192다.

| 시나리오 | 원문 글자 수 | generate 입력/출력 토큰 | 결과 | 실패 내용 |
| --- | --- | --- | --- | --- |
| 01 헬프데스크 | 728 | 4215 / 3600 | 완료 | — |
| 02 장애 대응 | 854 | 4330 / 4194 | review 실패 (502 `invalid_review_reference`) | 검토 후보 2건의 evidence가 원문이 아닌 생성 설계 문구 인용 |
| 03 서비스 카탈로그 | 758 | 4237 / 4264 | validate 실패 (422 `structure_invalid`) | 원문에 없는 `catalog_item_archive` 테이블 추가, PK 없음·추적 누락 |

Swagger에서도 같은 유형의 422(`traceability: 테이블 추적 누락`)가 발생했다. 로컬 보고서는 `backend/.debug-runs/20261007T053124-44226ac1/`(02), `20261007T053221-0ab172b1/`(03)이며 Git 관리 대상이 아니다.

## 원인 판단

- 입력 길이나 출력 한도 문제가 아니다. 01과 03의 길이 차이는 30자이고 출력은 한도의 약 절반이다.
- 이전 원문에 있던 지시성 문장(애플리케이션 검사, UUID 부여 등)을 빼자 모델이 설계 결정을 스스로 내리는 범위가 넓어졌다. 이 과정에서 원문에 없는 테이블을 만들거나 생성 설계를 원문처럼 인용했다.
- 생성 프롬프트에는 이미 "모든 테이블은 추적표에 나타나야 한다"가 있다. 규칙이 없어서가 아니라 모델이 확률적으로 위반하며, 현재 MVP는 위반을 고칠 기회 없이 바로 실패시킨다.
- 검증이 결함을 막은 것은 의도된 동작이다. 개선 대상은 검증 완화가 아니라 생성·검토 단계의 준수율이다.

## 개선 방향 (미결정)

1. 프롬프트 보강: 원문 근거 없는 보관·코드 테이블 생성 금지, 테이블별 단일 PK, 검토 evidence는 source에서만 인용한다는 규칙을 관찰된 실패 유형 기준으로 추가한다.
2. 검증 오류 피드백 1회 수정: validate 또는 review 참조·인용 검사가 실패하면 오류 목록과 직전 출력을 모델에 돌려주고 1회 수정한다. 장기 사양의 "단계별 최초 시도 외 최대 1회, 형식 복구·일시 오류 합산"을 MVP에 적용하는 것이다.
   - 수정본도 같은 검사를 통과해야 성공이다. 여전히 실패하면 현재처럼 422·502를 반환하며 샘플로 대체하지 않는다.
   - 수정 호출은 `model_calls`에 별도로 기록해 최초 결과와 수정 결과를 구분한다.
   - 검증 규칙 자체는 완화하지 않는다.

1과 2를 함께 적용하는 안을 권장한다. 2는 현재 MVP 문서의 "자동 수정·재시도하지 않는다" 정책을 바꾸므로 사용자 확인 후 진행한다.

## 수용 기준 (안)

- 대표 시나리오 3종을 실제 모델로 실행해 성공률과 수정 발생 여부를 기록한다. 1회 성공을 일반 성능으로 주장하지 않는다.
- 오류 주입 테스트로 수정 성공, 수정 후에도 실패, 수정 호출 기록을 외부 호출 없이 검증한다.
- 변경 시 기능 명세서·TRD·001 실행 계획·README의 재시도 설명을 함께 맞춘다.
