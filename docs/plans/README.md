# 기획 및 설계 문서 관리

이 폴더는 ITSM 설계 에이전트의 최신 기획·설계 기준을 관리한다. 현재 다섯 문서는 개발팀 검토용 초안이며 구현 완료 상태를 의미하지 않는다.

## 문서 목록과 역할

| 문서 | 답하는 질문 | 버전 | 문서 상태 | 내용 기준일 |
| --- | --- | --- | --- | --- |
| [프로젝트 기획서](프로젝트_기획서.md) | 왜 추진하며 범위·일정·산출물은 무엇인가? | 0.3 | 검토 중 | 2026-10-07 |
| [PRD](PRD.md) | 누구의 어떤 문제를 해결하고 무엇을 MVP로 제공하는가? | 0.3 | 검토 중 | 2026-10-07 |
| [요구사항 정의서](요구사항_정의서.md) | 반드시 충족할 조건과 수용 기준은 무엇인가? | 0.2 | 검토 중 | 2026-10-07 |
| [기능 명세서](기능_명세서.md) | 입력·출력·흐름·예외·화면 동작은 무엇인가? | 0.2 | 검토 중 | 2026-10-07 |
| [TRD](TRD.md) | 어떤 구조와 계약으로 구현·검증하는가? | 0.3 | 검토 중 | 2026-10-07 |

읽는 순서는 기획서 → PRD → 요구사항 → 기능 → TRD다. 문서 상태는 `작성 중 → 검토 중 → 확정 → 대체됨`으로 관리한다. 코드의 구현·검증 상태와는 별개다. 확정 후 수정안은 다시 검토 중으로 표시한다.

## 변경 시 함께 확인할 문서

| 변경 종류 | 주 기준 문서 | 영향 확인 |
| --- | --- | --- |
| 목표·일정·대상 업무 | 기획서 | PRD, 요구사항 |
| 사용자·MVP 범위·성과 목표 | PRD | 기획서, 요구사항, 평가 계획 |
| 필수 동작·수용 기준 | 요구사항 정의서 | 기능 명세서, TRD, 테스트 |
| 입력 제한·상태·예외·다운로드 정책 | 기능 명세서 | 요구사항, TRD, UI·API |
| API·DB·스키마·기술 구성 | TRD | 기능 명세서, 코드·테스트 |

특히 입력 상한, 실행 상태, 재시도 횟수, DDL 검증 및 다운로드 규칙은 문서 간 값이 일치하는지 확인한다. 현재값의 상세 기준은 기능 명세서이며, 기술 구현은 TRD에서 설명한다. 실제 구현과 다르면 TRD 또는 실행 계획에 기록하고 계획을 실적처럼 수정하지 않는다.

## 개발 실행 계획

- [002 시나리오 디버깅](tasks/002-시나리오-디버깅.md): 완료 (0.4, 2026-10-07) — 대표 시나리오 3종·시나리오 선택, 로컬 진단 검증, 루트 실행 명령 통일.

- [001 백엔드 MVP](tasks/001-백엔드-MVP.md): 완료 (0.3, 2026-10-07) — 사용자 확정 범위 구현·실제 Claude 호출 확인; Langfuse 원격·생성 DDL DB 실행은 미검증.

여러 단계가 필요한 기능 개발을 시작할 때만 `docs/plans/tasks/`를 만들고 `001-문서-분석.md`처럼 작업별 계획을 추가한다. 단순 문구 수정은 별도 계획이 필요 없다. 아직 시작하지 않은 구현을 완료 체크하지 않는다.

작업 계획에는 다음 내용을 기록한다.

- 상태: 예정 / 진행 중 / 대기 / 완료
- 목적, 범위와 제외 범위
- 관련 FR·NFR·AG ID 및 문서 링크
- 구현 단계와 실제 진행 체크리스트
- 검증 방법, 실행 결과, 남은 문제
- 업무·기술 결정과 이유, 관련 기준 문서의 갱신 여부

완료한 계획은 같은 경로에서 완료 상태로 유지한다. 기존 문서를 복제해 작업 계획으로 사용하지 않는다. 기획·설계의 최종 결정은 기준 문서에 반영하고 작업 계획에는 결정 이유와 구현 증거를 남긴다.

## 향후 폴더 확장

실제 자료가 생길 때만 다음 폴더를 추가한다.

- `docs/evaluation/`: 평가 절차, 실측 결과와 실패 분석
- `docs/decisions/`: 여러 대안을 비교한 중요한 기술·업무 결정
- `docs/plans/tasks/`: 기능별 구현 계획과 진행 기록

생성한 고객 설계 결과나 평가 입력은 기준 문서 폴더에 섞지 않는다. 실행 결과 저장 위치는 앱 설정과 TRD를 따른다.
